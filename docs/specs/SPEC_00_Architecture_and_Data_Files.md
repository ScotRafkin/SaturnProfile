## 0. What this document is

This is a specification of structure, not of code. It fixes the repository layout, the Python
package structure, the kinds of data file the system reads and writes, the two control files, and
the provenance rules every file obeys. It says what the files are and what they must contain. It
does not say how to write the tools or the model, does not prescribe an implementation order, and
does not specify tests. Those come in later `SPEC_` documents, one per module, each of which will
cite this one.

The manuscript, `CASSPIAN_AtmosphericModel.docx`, is the physical specification. Equations are
cited here by their manuscript numbers (A1 to A40, B1 to B8). Where this document and the
manuscript disagree, that is a defect in one of them and is to be raised, not patched around.
`CASSPIAN_Handoff_Coding_Phase.md` §9A is authoritative, for the Lindal profile, on its anchor
latitude and anchor radius, and in general on the harmonic expansion; it supersedes the
manuscript's §B1 and §B3.2 on those points until the manuscript is revised. Every profile has its
own anchor latitude and anchor radius, determined by the same procedure from its own source.

Everything in the existing repository predates this specification. It is to be assessed against
this document, not assumed to conform to it.

## 1. Principles

These are the rules the layout and the file formats exist to enforce. Each later section is an
application of one or more of them.

1. **The reverse-engineering boundary of §B1 is a boundary in the code and on disk.** Everything
   that reduces a published profile to refractivity runs once per profile, uses only that
   profile's own data and assumptions, and is then frozen. Everything that transfers refractivity
   and produces temperature and pressure is chosen per run. The two never share a control file, a
   directory, or a default. The single scalar that crosses the boundary is the declared boundary
   pressure `p_b` (§B7.2), and it crosses in the namelist, explicitly.

2. **Data lives in netCDF; choices live in TOML; neither holds the other.** Every number the model
   consumes comes from a self-describing netCDF file with units, provenance, and a citation. A
   control file holds pointers to those files and the run's declared choices. A physical value in
   a control file is a defect.

3. **One kind per file, and the kind is declared in the file.** A file is a thermodynamic
   profile, or a composition, or a geodesy, or a harmonic set, or a rotation system, or a wind
   field, or a refractivity product. It is never two of these. The reader validates the declared kind before
   anything else.

4. **Conventions travel with the numbers.** A latitude carries its convention in its name. A
   harmonic set carries its normalization radius and GM as variables. A wind carries its rotation
   system by name and by value. A bare number named `latitude` or `J2` is a defect.

5. **The model reads only model-ready files and refuses anything else.** Conversion between
   conventions, extension of observed fields, parameterization of unobserved regions, and the
   decomposition of the wind are done by tools that write files. The model never invents, never
   extrapolates, and never converts a convention.

6. **Provenance is by content hash.** Every derived file records the SHA-256 of every file it was
   made from, the tool and version that wrote it, the package git commit, and the time. A product
   can always be traced to exactly the inputs that made it.

7. **The library is pure.** Functions in [S1] take every physical input as an explicit argument.
   There are no module-level Saturn constants, no default harmonic sets, and no default rotation
   rates anywhere in the package. Physical constants of nature (§4) are the only module-level
   values.

8. **Every file used to make a product is copied beside it under the product's prefix.** Disk is
   free. Ambiguity about which harmonic set a reduction used is not.

### 2.1 `data_static/` [D0]

Curated transcriptions of published values that are not specific to one profile and not specific
to one run: the master species table, harmonic sets, rotation systems, published wind tables,
thermal retrievals. They change rarely, whether by hand or by a transcription script, and are
never read by `refrac` or `forward`.
Tools read them and write model-ready copies into [D1a] or [D2a]. The format of a static file is
whatever is most faithful to the source (a CSV transcription of a printed table, a netCDF of a
downloaded retrieval); the tool that consumes it is responsible for knowing that format. A static
file carries a companion text note stating where the numbers were read from. No value that
appears in a static file may be hard-coded in any tool; the tool reads the file.

`data_static/` is not the home of physical constants of nature. See §4.

### 2.2 `occul_data/<profile>/` [D1a]

One directory per published profile, named by a short slug (`lindal`, and later for example
`schinder2011_a`). Every file in it carries the slug as a prefix. The directory holds, in the
order they are made:

```
occul_data/lindal/
    raw/
        lindal_table1.csv         ASCII transcription of Table I (p, T, NH3, h)
        lindal_scalars.toml       every scalar the source states: latitude and swath,
                                  composition and its uncertainty, geoid fit parameters,
                                  citations; each with the page or figure it was read from
        lindal_raw.nc             the raw bundle, §2.2.1, built from the two files above
        notes.md                  transcription notes
    lindal_build.toml             control file for the stage-two tool, §2.2.2
    lindal_thermo.nc              kind T, §6.1
    lindal_composition.nc         kind C, §6.2, the reduction composition
    lindal_geodesy.nc             kind D, §6.3, the source's fitted reference surface
    lindal_gravity.nc             kind G, §6.4, the source's harmonic set
    lindal_rotation.nc            kind R, §6.5, the source's rotation system
    lindal_wind.nc                kind W, §6.6, the source's cloud-top wind
    lindal_reduction.toml         the reduction manifest, §7.1
    lindal_refractivity.nc        kind N, §6.7, the product of refrac
```

Two profile-specific tools stand between the ASCII and the model inputs (§3.2, and
`SPEC_01_Lindal_Tool_Chain.md` for the Lindal instance). The first turns the transcriptions into the
raw bundle. The second, driven by `lindal_build.toml` (§2.2.2), turns the raw bundle plus the
static transcriptions of [D0] into the six standard input files and the manifest, calling the
generic tools for the conversions. No physical value is hard-coded in either tool: the profile's
own values come from the raw bundle, and shared values (harmonic sets, rotation systems, wind
tables, species properties) come from [D0] by pointer. `refrac` reads only the standard files and
neither knows nor cares which profile they describe. After `refrac` has
run, the directory is complete and is not written to again unless the reduction is redone from
the start. Nothing under `forward/` may write here.

#### 2.2.1 The raw bundle (`raw/<profile>_raw.nc`)

A profile-specific netCDF that holds everything the source published, grouped however is most
faithful to the source: the tabulated profile, the trace species column, the stated composition,
the fitted geoid parameters, the latitude and swath, the citations for gravity, rotation and wind.
It has no standard schema beyond the §5 global attributes, because its purpose is to be a
complete and checkable transcription, not a model input. It is the file a reviewer opens to ask
"what did Lindal actually say," and it is the profile-specific input of the second tool. Grouping
thermo and geodesy together here is correct; separating them is the job of the second tool.

The ASCII transcriptions it is built from are data, not control, even though one of them is a
TOML file: `lindal_scalars.toml` exists because a printed paper states scalars in prose and
captions, and a keyed text file with a `value_source` beside every number is the most checkable
way to transcribe them. Principle 2 forbids physical values in *control* files; a transcription
file is a data file in a text format.

#### 2.2.2 The build control file (`<profile>_build.toml`)

Every tool that writes a netCDF file is driven by a TOML control file, on the same rules as the
model's control files (§7): pointers and choices, no physical values. For the stage-two profile
tool the choices are: which harmonic set, rotation system, and wind table under [D0] stand for
what the source used; which species table supplies the reduction refractivities; how the trace
species column is filled and normalized; the observation level assigned to the source's wind;
the output prefix. The hash of the control file is recorded in every file it produces. The full
vocabulary is specified with the tool, in `SPEC_01_Lindal_Tool_Chain.md`. The same pattern applies to
the generic tools of §3.2 when they are run on their own to build forward-run inputs under
[D2a]: a `<run>_build.toml` beside the namelist.

The reduction copies of `lindal_gravity.nc`, `lindal_rotation.nc`, and `lindal_wind.nc` are the
same file kinds as the forward-run copies under [D2a]. Kind D has no forward-run counterpart
(§6.3). They are different instances in a different
role. A forward run that wants Voyager-era harmonics gets its own copy under its own prefix; the
hashes will show the two are identical.

### 2.3 `forward/<run>/` [D2a]

One directory per forward run, named by the user. It holds the namelist at the top, the run's
inputs in `inputs/`, and the products in `output/`:

```
forward/baseline_cassini/
    baseline_cassini.toml         the run namelist, §7.2
    inputs/
        baseline_cassini_composition.nc     kind C
        baseline_cassini_gravity.nc         kind G
        baseline_cassini_rotation.nc        kind R
        baseline_cassini_wind.nc            kind W
    output/
        (forward products; schema in a later SPEC)
```

The namelist points at files under `inputs/` by relative path and at exactly one thing outside
its own directory: the registered refractivity product(s) under [D1a]. The tools write `inputs/`;
`forward` writes `output/` and writes nothing else anywhere. A run directory is therefore
self-contained and can be archived, copied, or diffed as a unit. A Monte Carlo [D2b] is a
directory of such directories.

### 2.4 Git

`.gitignore` currently excludes `*.nc`. That rule must be narrowed so that the registered products
under [D1a] and the inputs under [D2a] can be committed when wanted, while transient forward
output can be excluded. The raw digitizations under `raw/` and everything under [D0] are committed
as the canonical sources; generated netCDF under [D1a] is regenerable from them but is small and
should be committed once the reduction is accepted, since it is the anchor of every run.

## 3. Package structure [S]

Single Python package `casspian` under `src/`, installed in editable mode, with four subpackages.
Imports read `from casspian.lib import gravity`. Tools and drivers are console entry points
declared in `pyproject.toml`, not loose scripts.

### 3.1 `casspian.lib` [S1]

Pure functions. Every physical input is an argument. No I/O except in the two I/O modules. The
module list below is indicative; the coding agent may split or merge, but the boundaries between
lib, tools, refrac, and forward are fixed.

| Module | Implements | Notes |
|---|---|---|
| `constants` | CODATA physical constants | see §4 |
| `thermo` | ideal gas relations, Eq. A9, mean molar mass and mean molecular refractivity from mole fractions | the only place `R_bar` and `script_R` are formed |
| `gravity` | Newtonian potential and its derivatives, handoff §9A.5; Eqs. A2, A3, A4, A5 | takes GM, the J array, the normalization radius, the rotation rate, and the wind as arguments |
| `geoid` | Eq. B3; Lindal Appendix Eqs. 11 to 14; the no-wind reference geoid | takes the same arguments plus the polar radius |
| `latitude` | the planetographic to planetocentric fixed point, handoff §9A.2; ellipsoid seed | takes the full gravity components as arguments |
| `schema` | the file kinds of §6 as declared structures; validation; content hashing | |
| `io` | netCDF read and write for each kind; embedding of input copies as groups | |
| `control` | TOML reduction manifest and run namelist: parse, validate, resolve paths, serialize the resolved form | |

Naming rule from handoff §4.1: the mean specific gas constant is `R_bar`, the mean molecular
refractivity is `script_R`, and nothing is named `R`.

Return-type rule: `io.read` returns an `xarray.Dataset` for kinds without groups (T, D, G, R,
W) and an `xarray.DataTree` for kinds with groups (C, N, raw). The type is fixed by the kind,
never by the content of a particular file.

Array rule: numerical functions in `lib` take and return NumPy arrays with explicit arguments
and never accept an xarray object. `io` reads and writes every kind as an xarray Dataset, and
`forward` carries its labeled fields as xarray objects between `lib` calls, unwrapping to NumPy
on the way in and wrapping on the way out. No Python-level loop over array elements anywhere in
`lib`, `refrac`, or `forward`; the hot paths are whole-array operations. This keeps `lib`
translatable to a compiled language later without touching its interfaces.

### 3.2 `casspian.tools` [S2]

Tools read [D0] and `raw/` and write model-ready files into [D1a] or [D2a]. Each tool writes one
file kind, is invoked by a person from the command line, and takes a TOML control file (§2.2.2)
that names its inputs and its choices. No tool contains a physical value. Generic tools:

- `tools/wind/`: digitize or ingest a published wind table; convert its latitude axis through
  the fixed point of `lib.latitude`; assign the observation level; extend vertically by a
  declared parameterization, including the deep region below the observations; derive the
  sheared component from a thermal field by Eq. A39 when that is the source; decompose the full
  field into the cylinder-constant and sheared components about a declared reference level;
  write kind W.
- `tools/composition/`: build abundance profiles from parameters or from ingested model output;
  attach the species group from the master table; enforce normalization; write kind C.
- `tools/gravity/`: write kind G from a transcribed harmonic set and kind R from a rotation
  system entry.

Source-specific tools, one directory per published profile:

- `tools/lindal/`: everything that knows Table I exists, in two stages. Stage one reads the
  ASCII transcriptions under `raw/` and writes the raw bundle `raw/lindal_raw.nc` (§2.2.1).
  Stage two reads only the raw bundle, calls the generic tools with Lindal's choices, and writes
  the six standard input files and the reduction manifest under [D1a]. Its specification is
  `SPEC_01_Lindal_Tool_Chain.md` (next). A future profile gets its own `tools/<profile>/` with the same
  two stages and nothing else changes.

### 3.3 `casspian.refrac` [S3]

The reduction, Appendix B3, plus the two constants that are frozen per profile: the anchor's
planetocentric latitude `phi_c` and the anchor isobar radius at that latitude, `r0(phi_c)`.
Handoff §9A derives them for Lindal; every profile gets its own pair by the same procedure from
its own G, R, W, and D. Source-agnostic: it
reads kinds T, C, D, G, R, W and a reduction manifest, and never anything under `raw/` or [D0].
In order:

1. B3.1: number density from the tabulated pressure and temperature, Eq. A9. The only use of
   either.
2. The planetocentric anchor latitude `phi_c` by the fixed point of handoff §9A.2, with the
   source's gravity (G), rotation (R), and wind (W).
3. The anchor isobar radius `r0(phi_c)` by Lindal's construction (handoff §9A.6), anchored at
   the source's fitted polar radius from the geodesy file (D), with G, R, W.
4. B3.2: absolute radius per level, Eq. B1.
5. B3.3: refractivity from number density with the reduction composition (C) and its embedded
   species properties, Eq. A9.
6. Write kind N with everything it consumed embedded.

It is thin orchestration of `lib` calls, and identical for every profile.

### 3.4 `casspian.forward` [S4]

Appendix B4 to B7: the geopotential coordinate, the kernels, the isobar tracing, the transfer,
the estimation (an identity at M = 1, with the weight signature of Eq. A30 present), production,
and the delivered datum. Reads one or more kind N products and the run's C, G, R, W. Writes
`output/`. Its specification and its output schema come in later `SPEC_` documents. Two
statements belong here because they constrain the input files:

- The model's internal vertical coordinate is geopotential, per §A12. The wind input (kind W) is
  on pressure. The model owns the mapping between them, including the outer iteration it
  requires (§6.6), and the wind tool does not need a gravity model to write its file.
- The model refuses a wind file that does not cover the full pressure range the run will touch,
  rather than extrapolating (§6.6).
- The model does not read a geodesy file. The reference surface at every latitude is constructed
  by integrating Eq. B3 with the run's own G, R, W, from the constant of integration `r0(phi_c)`
  carried in kind N. The run's choice of geodesy is its choice of G, R, and W.
- The model does not decompose the wind. It builds effective gravity and the shear kernel from
  `u_total` and uses the stored components after checking them (§6.6).
- The command-line drivers of `refrac` and `forward` are thin: each takes a control file path,
  calls one function that does the work, and returns. Nothing in the model depends on running in
  a terminal or on the current working directory, so the same function can be invoked by a
  service that accepts a run directory and returns its `output/` (§11).

### 3.5 `casspian.tools.plots` (v0.11; v0.10 placed this as a top-level `diag` subpackage)

The standard diagnostics: a generic tool under `tools/`, tied to no profile, that renders a
fixed set of figures from a file alone, dispatching on the file's `casspian_kind` (kind N now;
the forward product later; single-figure views of input kinds W, T and C). Called by `refrac`
or `forward` after the product is written when the control file asks for it, and callable by
hand (`casspian-plots <file.nc>`). Figures are generated from the file, never from run state,
are written beside the product under `figures/`, are regenerable and are not committed.
Nothing in it computes a number that reaches a product. Specified in SPEC_02 Step 5.

## 4. Physical constants

Constants of nature (Boltzmann constant, atomic mass unit, Avogadro number, gravitational
constant, Loschmidt number if needed) live in `casspian.lib.constants` as CODATA values with the
CODATA release named in a module comment. They are not data in the sense of Principle 2: nobody
should be able to point a run at a different Boltzmann constant, and a netCDF file of them under
[D0] would invite exactly that. Every product records the CODATA release it was computed with in
its global attributes, so the values are traceable without being editable.

Everything Saturn-specific (GM, harmonics, radii, rotation rates, species properties) is data and
lives in files, never in `constants`.

**This is a decision that departs from the working assumption that constants go in `data_static/`,
made for the reason above. It is one line to reverse.**

## 5. Conventions common to every netCDF file

Format is netCDF-4. The following apply to every file of every kind.

**Global attributes, required.**

| Attribute | Content |
|---|---|
| `Conventions` | `"CF-1.10, CASSPIAN-0.1"` |
| `casspian_kind` | one of `thermo`, `composition`, `geodesy`, `gravity`, `rotation`, `wind`, `refractivity`, `raw` |
| `casspian_schema_version` | integer, per kind, bumped when the kind's schema changes |
| `title` | one line |
| `profile_or_run` | the slug the file's prefix carries |
| `role` | `reduction` or `forward` (kind N is always `reduction`) |
| `source` | full citation of the published source, or the tool and parameters for a generated field |
| `created_by` | tool name and version |
| `created_at` | ISO 8601, UTC |
| `casspian_git_commit` | commit hash of the package that wrote the file, with the suffix `-dirty` when the working tree had uncommitted changes; a file carrying `-dirty` is a development product and is never an input to a later step (§8) |
| `codata_release` | for any file that used a constant of nature |
| `input_hashes` | for any derived file: `"<relative path> sha256:<hex>"`, one entry per input, newline separated |
| `history` | append-only, one line per tool that touched the file |

**Naming.** Files are `<prefix>_<kind>.nc`. Variables are lower case with underscores. A latitude
variable or attribute is `latitude_planetocentric_deg` or `latitude_planetographic_deg`, never
`latitude`. A radius is `radius_m` (from the center of mass) or `height_m` (relative to a declared
datum), never `r` or `z` alone. Units go in the name where the quantity is otherwise ambiguous
(`_deg`, `_Pa`, `_m`) and always in the `units` attribute.

**Units.** SI throughout: Pa, K, m, m/s, kg/mol, rad/s, m³/s². Angles in degrees where they are
coordinates or stored scalars, and the `units` attribute says `degrees_north`. Pressure is in Pa
even though every source prints mbar; the conversion is done once, by the tool, and recorded in
`history`.

**Refractivity.** `N` is `n_refr − 1`, dimensionless, unscaled, with `units = "1"`. The
per-molecule refractivity `script_R_i` has units m³, defined so that `N = n Σ x_i script_R_i`
with `n` in m⁻³. Lindal's plotted and tabulated `N` is 10⁶ times this quantity; the tool that
transcribes any such value divides by 10⁶ and says so in `history`. **This is a decision; the
alternative of carrying the 10⁶ scaling is workable but invites a silent factor.**

**Uncertainties that are not known.** An uncertainty the source does not state is NaN, never
0.0; zero asserts perfect knowledge and a later error propagation would believe it. This applies
to transcriptions in `data_static/` as much as to netCDF files.

**Coordinates.** Every coordinate variable is strictly monotonic. A vertical coordinate (any
whose name contains `pressure`, `geopotential`, `height`, or `radius`) also carries a `positive`
attribute (`up` or `down`) and, for pressure, `direction` (`increasing` or `decreasing`) so a
reader never guesses; a coordinate with no vertical sense (`degree`, `species`, `surface`,
`latitude_planetocentric`) carries neither. Missing values are NaN with `_FillValue` set.

**Dimensions: absent, assumed, and missing are three different things.** Every kind that
describes a field is defined with its full set of dimensions (for T, C, and W: latitude and a
vertical coordinate). A file may omit a dimension, and when it does it must say why, in a
global attribute `<dimension>_absent_meaning` with one of two values. `uniform`: the quantity
does not vary along that dimension, and the reader broadcasts. `point`: the quantity is defined
only at the single coordinate value stated in a companion attribute (for latitude,
`latitude_planetocentric_deg` or the source convention's equivalent), and the reader refuses to
broadcast it; a model that needs the quantity elsewhere refuses. A dimension present with
identical values along it means the source assumed no variation, and the values carry a
provenance flag saying so. A NaN means no information at that location: the reader never fills
it, and filling is the job of a tool under a declared rule with a provenance flag. A dimension
of length one is allowed but discouraged, since it is the ambiguous case. The Lindal thermo
and composition files are `point` in latitude; a forward composition with no latitude
dependence is `uniform`; the Lindal wind is present, identical, and flagged. The kinds are the
same whichever side of the model a file sits on: a delivered temperature and pressure field is
a kind T, a retrieval consumed by the wind tool is a kind T, the wind a run used is a kind W.
Input and output share one schema and one reader.

**Per-variable attributes, required.** `units`, `long_name`, `provenance` (one of `measured`,
`derived`, `assumed`, `inferred`, `interpolated`, `parameterized`, `extrapolated`, `modeled`;
`modeled` means produced by `casspian.forward` and appears only in files the model writes;
`index` is for a coordinate or scalar that is a label rather than a measurement, such as
`degree`, `species_name`, `surface`, or kind N's `anchor_isobar_pressure_Pa`, which names a
level (v0.14). `derived` is a quantity obtained from measurements by a fit or a
computation with no additional physical assumption, such as a harmonic coefficient fitted to
tracking data or a pressure from a hydrostatic integration; `inferred` is a quantity deduced
through a model assumption the source declares, such as an ammonia abundance from an opacity
with an assumed line shape),
and where a value was read from a figure or a caption rather than a table, `value_source` (a
searchable string such as `"Fig. 4 label"`). Uncertainty variables are named by
inserting `_uncertainty` before the unit suffix of the variable they accompany
(`pressure_Pa` has `pressure_uncertainty_Pa`, `GM_m3s2` has `GM_uncertainty_m3s2`,
`u_total_ms` has `u_total_uncertainty_ms`); a variable with no unit suffix appends it
(`refractivity` has `refractivity_uncertainty`, `x_H2` has `x_H2_uncertainty`). The companion
has the same units and an `uncertainty_kind` attribute (`1sigma`, `range`, `stated`); how the number was obtained (a sample standard deviation of binned points,
a formal error, a quoted range) goes in a free-text `uncertainty_method` attribute, not in the
vocabulary. **Combining kinds (v0.13).** When a derived companion is formed from declared
uncertainties of different kinds, each is first converted to one standard deviation under a
declared rule and the result is `1sigma`: a `range` is the half-width of a uniform
distribution and is divided by √3; `stated` is taken as `1sigma` and the assumption is
recorded; the conversions applied are listed in an attribute `uncertainty_kind_conversions`
on the derived companion. A `x_H2_uncertainty` of 0.03 declared `stated` therefore enters as
0.03, and the 0.2° `range` on the Lindal label enters as 0.115°. Where the source's own words
make a different reading clearly right, the transcription declares the kind accordingly; the
rule converts what is declared.

**Types.** float64 for all physical quantities. Strings as netCDF string type or as attributes.
Status flags as int8 with a `flag_values` and `flag_meanings` pair, CF style.

## 6. The file kinds

Letters T, C, D, G, R, W, N are the ones used in Figure 1. Every kind is a model input in a
standard form; none of them knows which profile or run it belongs to except through its prefix
and its provenance attributes. Where a Lindal value appears below (36.3, "Fig. 4 label", System
III, Null et al.) it is an example of what the attribute holds for that profile, not part of the
schema; another profile fills the same attributes with its own values.

### 6.1 Kind T: thermodynamic field (`<prefix>_thermo.nc`)

Pressure and temperature on (latitude, level), with the vertical coordinate declared. No
composition and no geodesy is in this file. Instances: a published occultation profile (one
latitude, the latitude dimension absent; the vertical coordinate is the source's own pressure,
with the measured height carried alongside); a thermal-infrared retrieval T(φ, p) consumed by
the wind tool; the forward model's delivered field on its own grid.

Dimensions: `level`, and `latitude_planetocentric` when present.

| Variable | Units | Provenance | Notes |
|---|---|---|---|
| coordinate: `pressure_Pa(level)` or `geopotential_m2s2(level)` | | declared by the global attribute `vertical_coordinate` |
| `latitude_planetocentric_deg(latitude_planetocentric)` | degrees_north | | absent for a single profile |
| `pressure_Pa(...)` | Pa | `derived` or `modeled` | for a source profile this is the coordinate itself; used only in B3.1 |
| `temperature_K(...)` | K | `derived` or `modeled` | used only in B3.1 for a source profile |
| `height_m(level)` | m | `measured` | source profiles only: above the datum in `height_datum`; the measured quantity |

`retrieval`, or `model_output`. For a source profile the global attributes below are required
and the latitude of the profile is a global attribute in the source's convention (converted
later, never here). For the other two instances the latitude is the coordinate variable (or the
file is `point` in latitude with the planetocentric value stated) and the profile-specific
attributes are absent.

Global attributes beyond §5:

| Attribute | Content, Lindal instance |

| `longitude_deg`, `longitude_system` | `186.8`, `"System III"` |

### 6.2 Kind C: composition (`<profile>_composition.nc` or `<run>_composition.nc`)

Abundances plus the properties of every species named. Used in two roles: the reduction
composition (must reproduce what the source assumed) and the forward composition (chosen).

Dimensions: `level`, and optionally `latitude_planetocentric`.

| Variable | Units | Notes |
|---|---|---|
| coordinate: `pressure_Pa(level)` or `geopotential_m2s2(level)` | | which one is declared by the global attribute `vertical_coordinate` |
| `latitude_planetocentric_deg(latitude_planetocentric)` | degrees_north | optional; absent means uniform in latitude |
| `x_<species>(level[, latitude])` | mol/mol | one variable per species; `provenance` per variable |
| `x_<species>_uncertainty` | mol/mol | Lindal H2: 0.03, `uncertainty_kind = "stated"` |

Constraint: at every point the mole fractions sum to one within 1e-9. The tool enforces it; the
reader checks it and refuses the file otherwise. **The closure is declared, not inferred
(v0.13):** global attributes `closure_rule` (`"share_of_remainder"`: the species in
`closure_species` are assigned last as a fixed share of the remainder after the others; or
`"normalized"`: all species scaled to sum to one) and `closure_species` (for
`share_of_remainder`, the share species then its partner, `"H2 He"` for Lindal), written by the
composition tool and read by `refrac`, which checks the declaration against the values and
refuses on disagreement. The constrained uncertainty derivative of SPEC_02 Step 3 is taken
under the declared rule. How a tool arrives at normalized fractions (for
Lindal: NH3 interpolated and extrapolated in pressure, clamped at zero, remainder split 0.94 to
0.06) is specified in that tool's SPEC and recorded in `history`, not here.

Group `species`. Dimension `species` with a string coordinate `species_name`. Variables:

| Variable | Units | Notes |
|---|---|---|
| `molar_mass_kg_mol` | kg/mol | |
| `refractivity_per_molecule_m3` | m³ | `script_R_i`, §5 |
| `refractivity_frequency_Hz` | Hz | the frequency the value applies to |
| `refractivity_uncertainty_m3` | m³ | NaN where the source states none (§5, v0.7), never 0.0 |
| `refractivity_temperature_dependence` | flag | 0 none, 1 declared in `refractivity_temperature_note` |
| `is_polar` | flag | |
| `citation` | string | per species |

Group attributes: `master_table` (path under [D0]) and `master_table_hash`. The group's schema is
identical in every kind C file; the tool generates it from the master table so that a change in
one species value propagates by regeneration, never by editing a file.

Global attribute `composition_role`: `reduction` or `forward`. A reduction composition also
carries `source_statement`, the source's own words (`"94% H2 with the remainder being He and
NH3"`).

### 6.3 Kind D: geodesy (`<profile>_geodesy.nc`)

The source investigation's fitted reference surfaces. A reduction-phase input only: `refrac`
reads it to anchor Lindal's geoid construction at the fitted polar radius (handoff §9A.6), and
`forward` refuses it (§3.4). It is a separate kind from T because the retrieval and the geoid fit
are different measurements with different error budgets, and because the forward run's geodesy
is its choice of harmonics, rotation, and wind, not a fitted surface.

Dimension `surface` with coordinate `surface_pressure_Pa` (values 1e4 and 1e5 for Lindal).

| Variable | Units | Notes |
|---|---|---|
| `radius_equatorial_m(surface)` | m | with `radius_equatorial_uncertainty_m` |
| `radius_polar_m(surface)` | m | with `radius_polar_uncertainty_m`; the anchor of the construction |
| `oblateness(surface)` | 1 | with `oblateness_uncertainty` |
| `fit_residual_m(surface)` | m | standard deviation of the fit where the source gives it per surface; NaN otherwise, with a range the source states as a whole carried in `fit_residual_range_m = [lo, hi]` and its quotation in `fit_residual_source` (v0.9) |

Global attributes: `citation`; `fit_inputs`, the source's own statement of what went into the fit
(harmonics, rotation system, wind, and the assumption of altitude-independent wind, quoted);
`fit_latitude_convention` for the abscissa of the source's figure (planetocentric for Lindal's
Fig. 9). The reduction manifest names which surface anchors the construction.

### 6.4 Kind G: gravity harmonic set (`<prefix>_gravity.nc`)

Dimension `degree` with integer coordinate `degree` (values 2, 4, 6, ...).

| Variable | Units | Notes |
|---|---|---|
| `J(degree)` | 1 | unscaled (the printed value times 1e-6) |
| `J_uncertainty(degree)` | 1 | |
| `J_status(degree)` | flag | 0 fitted, 1 assumed, 2 constrained |
| `GM_m3s2` | m³/s² | scalar |
| `GM_uncertainty_m3s2` | m³/s² | scalar |
| `normalization_radius_m` | m | scalar; a property of the set |

Global attributes: `GM_scope` (`planet` or `system`, with a note), `uncertainty_scaling` (Iess et
al. 2019: three times formal), `epoch`, and `harmonic_convention`, a short code naming the
convention the coefficients obey. The only code defined is `CASSPIAN-J1`, which means: even
zonal harmonics `J_l` of degree `l`, unscaled (printed value times 1e-6), in the potential
`V = −(GM/r) [1 − Σ J_l (R/r)^l P_l(sin φ_c)]` with `R` the normalization radius stored in
the file, `φ_c` planetocentric, and `g_N = ∂V/∂r` positive inward (handoff §9A.5). The code is
defined once, in `lib.schema`, with this sentence beside it. The reader refuses a file whose
code it does not know. A different convention (tesseral terms, a different sign, normalized
coefficients) gets a new code, never a reinterpretation of an old one.

The two sets needed now are Null et al. (1981) at 60,000 km (J6 = 84 assumed) and Iess et al.
(2019) at 60,330 km. GM for each is an open item (§9).

### 6.5 Kind R: rotation system (`<prefix>_rotation.nc`)

Scalars `period_s`, `angular_rate_rad_s`. Global attributes `system_name` (`"System III"`),
`epoch`, `citation` (Desch and Kaiser 1981). Tiny by design; its existence as a file lets a wind
file reference a rotation system by name and carry its value, and lets a reader compare the two.

### 6.6 Kind W: wind field (`<prefix>_wind.nc`)

The single dynamical input to the model. The full field on the model's own axes together with
its two components, all three as data, plus enough provenance to say where every value came from.
The tool that writes the file is responsible for the decomposition, whichever direction it was
built in (total then split, or cylindrical plus shear then summed). The model never decomposes.

Dimensions: `latitude_planetocentric`, `pressure`.

| Variable | Units | Notes |
|---|---|---|
| `latitude_planetocentric_deg(latitude_planetocentric)` | degrees_north | coordinate |
| `pressure_Pa(pressure)` | Pa | coordinate |
| `u_total_ms(latitude, pressure)` | m/s | positive eastward, relative to the declared rotation system; the field the model builds `g` (Eq. A4) and the kernel (Eq. A15) from |
| `u_cylindrical_ms(latitude, pressure)` | m/s | the component with `Omega_abs` constant on cylinders concentric with the rotation axis, fixed by the field at `reference_level_pressure_Pa` |
| `u_shear_ms(latitude, pressure)` | m/s | `u_total` minus `u_cylindrical`; the component that carries the whole of the axial derivative |
| `u_total_uncertainty_ms` | m/s | |
| `value_provenance(latitude, pressure)` | flag | 0 observed, 1 interpolated, 2 parameterized, 3 extrapolated, 4 extended_by_source_assumption |
| `decomposition` | string attribute | `"trivial_altitude_independent"` when `u_cylindrical = u_total` and `u_shear = 0` by declaration (no radius per level in the file), otherwise the geometry named in `decomposition_geometry` (v0.8) |
| `reference_level_pressure_Pa` | Pa | scalar; the level defining the decomposition |

Global attributes:

| Attribute | Content |
|---|---|
| `rotation_system_name`, `rotation_rate_rad_s` | must equal the run's or manifest's kind R file |
| `epoch` | of the observations |
| `method` | `"cloud tracking"`, `"thermal wind from <retrieval>"`, `"parameterized"`, or a combination |
| `observation_level_Pa`, `observation_level_justification` | where the observed wind was assigned and why |
| `source_latitude_convention` | `planetographic` or `planetocentric`, as published |
| `latitude_conversion_inputs` | when converted: the gravity, rotation, and wind files (paths and hashes) used in the fixed point |
| `vertical_structure` | `"altitude independent"`, `"parameterized: <form>"`, or `"two-dimensional from <source>"` |
| `parameterization` | the functional form and every parameter, as a TOML fragment in the attribute |
| `decomposition_geometry` | the geoid (inputs and hashes) on which `u_cylindrical` was computed |
| `coverage_pressure_Pa` | `[min, max]` |
| `coverage_latitude_planetocentric_deg` | `[min, max]` |

Rules the model enforces at load time:

- The file's `rotation_system_name` and rate match the kind R file the run points to; otherwise
  refuse.
- `coverage_pressure_Pa` spans from above the declared boundary pressure to below the deepest
  level the run delivers, and `coverage_latitude` spans every target latitude and every anchor
  latitude; otherwise refuse. The model does not extrapolate the wind.
- The identity `u_total = u_cylindrical + u_shear` holds at every point to round-off; otherwise
  refuse.
- Both poles are nodes of the latitude coordinate and `u_total_ms` is exactly zero there at
  every level; otherwise refuse (v0.8). A zonal wind is zero at a pole by definition, and a
  nonzero value there makes `Omega_abs` and the meridional gravity singular (REPORT_01_step7,
  finding 5). The tool that writes the file, not the model, is where a source that does not
  reach the pole is brought to zero, under a declared and flagged rule.
- `Omega_abs` formed from `u_cylindrical` (Eq. A2) is constant along cylinders on the model's
  own geometry to a declared tolerance; otherwise refuse. The tool computed the split on a
  reference geoid, the run integrates on its own surfaces, and this check is what bounds the
  difference. The kernel is formed from `u_total`, by its definition in Eq. A15, so a residual
  within tolerance cannot be lost; the check exists so that the components the model reports
  and the components the tool wrote mean the same thing.

The reduction instance (Lindal's cloud-top wind, altitude independent, planetographic as
published, converted) and the forward instances are the same schema. For the reduction instance
`vertical_structure = "altitude independent"` and the pressure dimension may have length one with
coverage declared as the full range, since the value applies at every level by the source's own
assumption.

### 6.7 Kind N: registered refractivity product (`<profile>_refractivity.nc`)

Written by `refrac`. The only file under [D1] that `forward` reads. Everything the reduction
consumed is embedded so the file can be audited alone.

Dimension `level`.

| Variable | Units | Notes |
|---|---|---|
| `radius_m(level)` | m | absolute, Eq. B1; coordinate |
| `height_above_anchor_isobar_m(level)` | m | `h − h_ref` from the thermo file |
| `number_density_m3(level)` | m⁻³ | B3.1 |
| `refractivity(level)` | 1 | B3.3 |
| `radius_uncertainty_m`, `number_density_uncertainty_m3`, `refractivity_uncertainty` | | first-order propagation of the declared input uncertainties only, uncorrelated between inputs, unstated terms left out; each carries `uncertainty_terms_included` and `uncertainty_terms_unstated` (v0.12, SPEC_02 Step 3) |
| `mean_refractivity_m3(level)`, `mean_molar_mass_kg_mol(level)` | m³, kg/mol | from the embedded composition and its species group (v0.10); every consumer needs them; with their uncertainty companions `mean_refractivity_uncertainty_m3` and `mean_molar_mass_uncertainty_kg_mol` (v0.13) |

Scalars with uncertainties: `latitude_planetocentric_deg` (`phi_c`), `psi_deg`,
`latitude_planetographic_deg` (copied from T), `anchor_isobar_pressure_Pa`,
`anchor_isobar_radius_m` (`r0`), `anchor_isobar_height_m` (`h_ref`). "Anchor isobar" is the
surface whose absolute radius anchors the profile (100 mbar for Lindal, the surface his geoid was
fitted on). The forward run's gauge isobar, where Phi = 0, is normally the same surface but is a
separate choice (§B5.2), so the two are named differently.

Groups, all required: `inputs/thermo`, `inputs/composition`, `inputs/geodesy`,
`inputs/gravity`, `inputs/rotation`, `inputs/wind`, each a verbatim copy of the input file's
variables and attributes; `manifest`, a group with no variables whose attribute `text` is the
reduction manifest verbatim and whose attribute `sha256` is its hash; `reduction_record`, a
group with no variables whose attributes record the fixed-point iterates of `phi_c`, the geoid
construction (`anchor_rule`, north polar start, both polar radii, polar asymmetry, anchoring
residual), the no-wind `phi_c` and `r0` for reference, the anchor-rule spread as a recorded
choice, the partial derivatives of the uncertainty propagation, and the CODATA release (v0.10,
v0.12).

Global `input_hashes` lists all six inputs and the manifest.

## 7. Control files

Both are TOML. Both hold pointers and declared choices only. A path may be absolute or relative;
a relative path is resolved against the directory containing the control file, and the resolved
(absolute) form is what gets recorded in products. A physical value that belongs in a data file
is refused by the parser (the parser knows which keys exist; an unknown key is an error, not a
warning).

### 7.1 Reduction manifest (`<profile>_reduction.toml`)

One per profile. Consumed by `refrac`. Everything in it is a property of the observation, chosen
once.

```toml
[profile]
slug        = "lindal"
description = "Voyager 2 ingress, Lindal, Sweetnam and Eshleman 1985, Table I"

[inputs]                       # all kinds, all under this directory, all prefixed
thermo      = "lindal_thermo.nc"
composition = "lindal_composition.nc"
geodesy     = "lindal_geodesy.nc"
gravity     = "lindal_gravity.nc"

[anchor_isobar]
pressure_Pa = 1.0e4            # the surface whose radius anchors the profile; the one the source fitted a geoid on

[anchor_latitude]
fixed_point_tolerance_deg = 1.0e-6
max_iterations            = 20

[geoid]
anchor_surface_Pa = 1.0e4      # which surface of the geodesy file anchors the construction
anchor_quantity   = "radius_polar_m"
anchor_rule       = "mean_polar_radius"   # SPEC_01 v0.16: how the one constant of Eq. B3 is fixed;
                                          # one of mean_polar_radius, north_pole, south_pole (anchor_quantity
                                          # radius_polar_m) or equatorial_radius (anchor_quantity
                                          # radius_equatorial_m, the equator an exact march node; v0.15)
```

One per forward run. Consumed by `forward`. Everything in it is chosen per run.

```toml
[run]
name        = "baseline_cassini"
description = "Cassini-era harmonics, Garcia-Melendo cloud winds with decay, Lindal composition"

[[anchors]]                    # one table per profile; the only pointers outside this directory
slug   = "lindal"              # must equal profile_or_run inside the file, or refuse

p_b_location = "top_of_anchor_profile"   # the only value accepted; present so the choice is visible

[isobars]
gauge_isobar_Pa = 1.0e4        # where Phi = 0, Eq. A13 and §B5.2; must be an isobar

[target]                       # one run, one latitude, one delivered profile

[grid]                         # proposal, open; see §7.3

latitude_spacing_deg      = 0.5                # uniform in phi_c; the step of the isobar tracing

[numerics]                     # proposal, open; see §7.3. One table per integration or fixed point,
                               # each with its own scheme and its own tolerance carrying units.
[numerics.geopotential]        # Phi = integral of g dz, Eq. B2
scheme = "trapezoid"
[numerics.shear_integral]      # I = integral of S/g dPhi, Eq. A16
scheme = "trapezoid"
[numerics.isobar_tracing]      # dPhi/dphi = -I, §B6.2
scheme = "rk4"
[numerics.transfer]            # integral of K dphi, Eq. A28
scheme = "trapezoid"
[numerics.hydrostatic]         # p by Eq. B5
scheme = "trapezoid"
[numerics.altitude]            # z by Eq. B8
scheme = "trapezoid"
[numerics.reference_surface]   # r0(phi) by Eq. B3

[numerics.outer_loop]          # wind and composition supplied on pressure; the p(Phi) fixed point of §B7.1
relative_tolerance_ln_p = 1.0e-8

[estimation]                   # Eqs. A30, A34, A35; an identity at M = 1
```

Rules: `forward` writes the fully resolved namelist (absolute paths, hashes, defaults filled) into
`output/` and into the global attributes of every product. `forward` refuses the run if the wind
and rotation files disagree, if any pointed-to file is not of the declared kind, if a `geodesy`
key is present at all, if any file under `inputs/` does not carry the run prefix, if
`p_b_declared_at` is anything other than the top of the anchor profile, or if the wind coverage
or component rules of §6.6 fail, or if `p_b_location` is anything other than
`top_of_anchor_profile`.

The manuscript's `p_b` uncertainty (Eq. B7) is not a model input. The model does not need it and
does not propagate it; if an ensemble wants it, the wrapper varies `p_b_Pa` directly.

### 7.3 Namelist items still under discussion

Recorded here so the vocabulary above is not read as settled.

- **Vertical grid.** The proposal is a uniform grid in geopotential for the first build, spacing
  declared, because the transfer delivers each level at a shifted geopotential and a uniform grid
  makes that re-gridding trivial, and because level and layer bookkeeping (handoff §13) is easiest
  to state and to check on a uniform grid. Pressure is exponential in geopotential, so a uniform
  grid over-resolves the deep end relative to the data (Table I is close to uniform in log p at
  ten levels per decade); at 5e3 m²/s² spacing the anchor span is about 900 levels, which costs
  nothing. A stretched grid, if the numerical methods document later argues for one, is a change
  to one function and one namelist key.
- **Latitude grid.** Uniform in planetocentric latitude. The isobar tracing is an ordinary
  differential equation in latitude whose step is this spacing; nothing in the formulation wants
  a sine or area-weighted grid.
- **Numerics.** Seven integrations and one fixed point are listed above, each with its own
  scheme so grid-convergence checks can vary them independently. Whether all seven need to be
  exposed, or a single default scheme with per-integration overrides is enough, is open.
  Tolerances carry units in their names; the outer loop tolerance is relative, on ln p, hence
  unitless. Two rules are fixed now and bind the numerical methods document: (i) across a layer,
  any quantity that is near-exponential in the coordinate (N, n, rho, p) is treated as
  log-linear and its layer integral is the exact integral of that exponential, never the
  trapezoid of endpoint values; quantities that are not (T, u, composition) are interpolated
  linearly; (ii) every variable and every derivative is assigned a location on a staggered
  (phi, Phi) grid, at levels or at half-levels and at latitudes or half-latitudes, in a table
  written and agreed before the first integral is coded, and layer quantities such as the
  hydrostatic density and the layer composition are formed from level values by a stated rule.
- **Estimation.** The model-error correlation length is a property of the kernel error (the wind
  field), so it is one number shared by all profiles. Per-profile quantities are the measurement
  uncertainties, which live in each profile's own file and can be scaled per anchor entry. Each
  anchor entry carries the profile's slug and the model refuses a mismatch with the file's
  `profile_or_run` attribute.

## 8. Provenance and refusal, collected

Every rule that a file or a reader enforces, in one place, so the coding agent can implement them
as one validation layer in `lib.schema` and `lib.control`.

**Writers.** Every file gets the §5 global attributes. Every derived file lists its inputs by
relative path and SHA-256. Every file under [D1a] or [D2a] carries the directory's prefix.
Uncertainty variables exist even when empty. Latitude and radius names carry their convention.
Pressure is Pa. Refractivity is unscaled.

**The rebuild rule is a property of the directory, not of a step (v0.9).** After every
acceptance commit, every product under `occul_data/` or `forward/` whose `casspian_git_commit`
carries `-dirty` is rebuilt, whichever step wrote it; a product rerun in passing from an
uncommitted tree (as happened to the Step 3 products during Step 7) is caught by that sweep and
by the check the Step 9 acceptance runs.

**Readers refuse when:** a file offered as an input to `refrac` or `forward` carries a
`casspian_git_commit` ending in `-dirty` (tools may read such files during development; the
model may not); the `casspian_kind` is not the kind asked for; a dimension is absent
without an `_absent_meaning` attribute, or a `point` file is asked for a value away from its
stated coordinate; the schema version is
newer than the reader; a required variable or attribute is missing; a coordinate is not
monotonic; mole fractions do not sum to one; a harmonic file's `harmonic_convention` is not the
known string; a wind file's rotation system differs from the rotation file; a wind file's coverage
does not span the run; a wind file's components do not sum to its total, or its cylindrical
component is not constant on cylinders on the model geometry to tolerance; a namelist or manifest
contains an unknown key; a namelist names a geodesy file; a namelist points at a file lacking the
run prefix; a manifest points outside its own directory; a namelist points outside its own
directory to anything but a kind N file.

**Readers warn when:** a `value_source` is absent on a value that is not from a table; an
`input_hashes` entry does not match the file now on disk at that path (the embedded copy remains
authoritative).

## 10. Decisions made in this document

Listed so they are visible rather than buried.

1. Constants of nature in `lib.constants`, not in `data_static/` (§4).
2. Refractivity stored unscaled, `n_refr − 1`, not times 10⁶ (§5).
3. Geodesy (kind D) is a reduction-phase input only; `forward` refuses it, because the forward
   reference surface is constructed from G, R, W and the frozen `r0(phi_c)` in kind N (§3.4,
   §6.3). Allowing a forward run to re-anchor at a chosen polar radius would be a different model.
4. In the wind file the model reads, total and components are all data; the model checks them
   (sum identity, constancy on cylinders) and refuses on failure rather than recomputing them
   (§6.6). The tool that writes the file may build it in either direction: a total that it
   splits, or components that it sums to a total. Which direction was used is recorded in the
   file's `history`.
5. TOML for both control files; unknown keys are errors (§7).
6. Generated netCDF under [D1a] is committed once accepted; `.gitignore` is narrowed (§2.4).
7. The raw bundle `raw/<profile>_raw.nc` has no standard schema beyond §5, by design (§2.2.1).

## 11. Language and deployment

Python, with NumPy in the numerical library and xarray at the I/O and field layer (§3.1). Python
is expected to be fast enough for the model and for a Monte Carlo wrapper that parallelizes over
runs; the array rule of §3.1 is what keeps `lib` translatable to C, C++, or Fortran if that ever
changes.

The model is proprietary to the Institute and its source is not to be distributed. No form of
shipped execution protects Python source (bytecode decompiles; obfuscators and compilers to
native code raise the bar, need per-platform builds, and remain recoverable). The working
assumption is therefore that the team uses the model as a service: a run directory (namelist plus
`inputs/`) is submitted to an Institute-controlled host and `output/` is returned, with the
source never leaving that host. The architecture requires nothing extra for this beyond the thin
drivers of §3.4. Whether the data-preparation tools are shipped to the team as source is a
separate judgment about what is proprietary, and is not made here.
